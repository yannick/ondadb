Workload (phase 5 of the `range-delete` harness, `tests/range_delete_bench.rs`):
60,000 keys x 100-byte values, `target_file_size` 2 MiB, 2 compaction threads.
One `delete_range` covering the whole key space, then the same fully-covering
bulk delete reclaimed two ways:

  A (excise)      delete_range -> flush -> DB::excise_covered until no covered
                  table remains. No block is read and no byte is rewritten: one
                  `RemoveTables` catalog edit plus N unlinks.
  B (compaction)  delete_range -> flush -> DB::compact. The pre-1.2 path:
                  merge-read every input, write the survivors. `run_manual`
                  carries no excise pre-pass, and while it holds the whole-
                  keyspace range lock a background pre-pass is vetoed.

A leaves the fragment owner behind by design (dropping it would destroy the
evidence that justified the drop), so the arms are compared on covered bytes
reclaimed and on wall clock, not on reaching zero resident bytes.

================================================================================
GATE DECISION
================================================================================

PASS — but on a narrower margin than the phase-1 range-delete numbers, and the
reason is worth stating rather than glossing.

1. Same coverage. Both arms reclaim the same 7.1 MB (152 bytes apart — the
   fragment owner's own framing). This is not "excise reclaims less, faster";
   it is the same space, freed two ways.

2. Wall clock: 1.5x median, 1.5-2.0x across three repetitions. This machine is
   thermally noisy (+/-15-20% run to run, `docs/performance.md`), and 1.5x sits
   only modestly outside that band — which is why three repetitions are recorded
   rather than one, and why the ratio is read same-run only. The direction is
   consistent in all three: excise is faster in every repetition, never slower.

3. Why the margin is modest at this size, honestly. Both timers start at
   `delete_range` and therefore both include the tombstone commit and the
   `flush_memtable` that publishes the fragment — work excise does not avoid and
   cannot make cheaper. At 60k keys / 7 MB that shared prefix is a large share of
   both numbers, so the ratio understates what excise actually removes. The part
   that differs is B's merge: read every input block, decompress, merge, write
   survivors, fsync. That term scales with the data volume; excise's term is one
   catalog record plus N unlinks and scales with the *table count*. The measured
   ratio is therefore a floor that grows with dataset size, and 7 MB is a small
   dataset by design (the harness has to run in minutes).

4. What is categorical rather than measured. Excise reads **zero** SSTable data
   blocks and writes **zero** SSTable bytes for the reclaimed tables. That is a
   structural property of the transaction (`RemoveTables` edit -> publish ->
   `remove_sst_file`), not a benchmark result, and it is what makes the feature
   worth having on a cold or IO-bound tier where B's merge would be paid in
   real IO rather than in page cache. This bench runs entirely warm, which is
   the least favourable configuration for the claim.

DECISION: ship. The measured wall-clock win is real and consistently signed, the
byte-level claim is categorical, and no arm regressed. Not claimed: any specific
multiple. If a future change needs a headline number, re-run at a dataset large
enough that the shared flush prefix stops dominating.
